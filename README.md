# SEO Master

SEO Master - веб-приложение для SEO-аудита, анализа проекта и контролируемого внедрения SEO-изменений через согласование человеком. Система помогает проверить сайт, сохранить его как проект, получить список задач, оценить качество страниц через FF-Score и безопасно подготовить изменения для WordPress или Tilda.

Рабочая версия проекта развёрнута на домене:

[https://сео-мастер.рф](https://сео-мастер.рф)

## Назначение проекта

SEO Master предназначен для владельцев сайтов, SEO-специалистов и администраторов, которым нужно не просто получить отчёт об ошибках, а довести рекомендации до управляемого внедрения.

Приложение решает несколько задач:

- проводит публичный SEO-аудит сайта;
- сохраняет сайты в личном кабинете как проекты;
- показывает историю аудитов и динамику качества;
- рассчитывает FF-Score и связанные метрики;
- формирует задачи на улучшение страниц;
- показывает изменения до публикации;
- позволяет подтвердить или отклонить предложенные правки;
- хранит историю внедрений и откатов;
- подключает WordPress, Tilda, GSC, GA4 и Yandex Webmaster на уровне проекта.

## Как работает веб-приложение

Пользователь работает с системой через сайт [https://сео-мастер.рф](https://сео-мастер.рф).

Общий путь выглядит так:

1. Пользователь открывает сайт и запускает SEO-аудит по адресу страницы.
2. После аудита можно зарегистрироваться или войти в личный кабинет.
3. Сайт сохраняется как проект.
4. В проекте отображаются аудиты, метрики, задачи и подключённые интеграции.
5. Для задач, требующих ручной проверки, создаётся HITL-согласование.
6. Пользователь видит сравнение текущего и предлагаемого состояния страницы.
7. После подтверждения система может передать изменение в подключённую CMS.
8. Результат внедрения фиксируется в журнале.

## Основные пользовательские сценарии

### 1. Быстрый SEO-аудит

На главной странице пользователь вводит адрес сайта или страницы. Система запускает аудит и возвращает результат: общий балл, найденные проблемы, проверенные страницы и рекомендации.

Этот сценарий подходит для первичной оценки сайта без настройки интеграций.

### 2. Личный кабинет

После входа пользователь попадает в панель управления. Там отображаются:

- количество проектов;
- активные аудиты;
- задачи, ожидающие решения;
- средний FF-Score;
- последние проекты;
- последние проверки.

Панель управления нужна, чтобы быстро понять текущее состояние всех сайтов.

### 3. Работа с проектом

В карточке проекта доступны:

- основная информация о сайте;
- статус проекта;
- последний аудит;
- FF-Score;
- количество аудитов, страниц, ключевых слов и обратных ссылок;
- история проверок;
- подключение внешних сервисов.

Проект является центральной сущностью системы: вокруг него собираются аудиты, задачи, интеграции и история внедрений.

### 4. История аудитов

Во вкладке аудитов можно посмотреть выполненные проверки, открыть подробный отчёт и сравнить состояние проекта во времени. Это помогает показать не только текущие ошибки, но и динамику работы над сайтом.

### 5. Интеграции

Во вкладке интеграций пользователь подключает внешние источники и CMS:

- WordPress;
- Tilda;
- Google Search Console;
- Google Analytics 4;
- Yandex Webmaster.

Для WordPress предусмотрена загрузка плагина, генерация HMAC-секрета и проверка подключения.

## Демонстрационный проект

Для защиты и демонстрации предусмотрен отдельный набор демонстрационных данных. Он создаёт проект, который выглядит как уже подключённый и обработанный WordPress-сайт.

В демонстрационном проекте есть:

- история завершённых аудитов;
- FF-Score и E-E-A-T данные;
- подключённые WordPress, GSC и GA4;
- задачи в разных состояниях;
- HITL-согласования;
- журнал внедрений;
- история успешных и неуспешных публикаций.

## Интеграция с WordPress

WordPress подключается через плагин SEO Master Connector. Пользовательский сценарий выглядит так:

1. Открыть проект в личном кабинете.
2. Перейти во вкладку интеграций.
3. Выбрать WordPress.
4. Скачать ZIP-архив плагина.
5. Установить плагин в WordPress через раздел "Плагины".
6. Сгенерировать HMAC-секрет в интерфейсе SEO Master.
7. Добавить секрет в конфигурацию WordPress.
8. Выполнить проверку подключения.

Плагин принимает подписанные изменения для:

- мета-заголовков и описаний;
- schema.org разметки;
- внутренних ссылок.

Архив плагина доступен в приложении по маршруту:

```text
GET /api/wordpress-plugin
```

Исходники плагина находятся в [adapters/wordpress-plugin](adapters/wordpress-plugin).

## HITL-согласование

HITL означает, что важные изменения не публикуются автоматически без решения пользователя.

В интерфейсе согласования пользователь видит:

- страницу, к которой относится задача;
- тип задачи;
- ожидаемое влияние;
- описание рекомендации;
- текущее состояние;
- предлагаемое состояние;
- поле для комментария;
- кнопки подтверждения и отклонения.

Такой подход нужен, потому что SEO-изменения могут влиять на смысл страницы, юридические формулировки, медицинские утверждения, коммерческие обещания и структуру сайта. Система готовит изменение, но финальное решение остаётся за человеком.

Подробное описание жизненного цикла HITL находится в [docs/HITL_WORKFLOW.md](docs/HITL_WORKFLOW.md).

## Что находится в репозитории

Основная структура проекта:

```text
.
├── adapters/                 # адаптеры для WordPress и Tilda
├── config/                   # конфигурация nginx, логирования и базы данных
├── database/                 # модели, миграции и начальная схема БД
├── docs/                     # проектная документация
├── frontend/                 # клиентское приложение React/Vite
├── scripts/                  # служебные скрипты, включая демонстрационные данные
├── services/                 # серверные микросервисы
├── tests/                    # модульные, E2E и нагрузочные тесты
├── docker-compose.yml        # основной состав серверных контейнеров
├── docker-compose.dev.yml    # состав контейнеров для разработки
├── docker-compose.prod.yml   # состав контейнеров для промышленного окружения
└── pytest.ini                # настройки pytest
```

Ключевые ссылки:

- [frontend](frontend) - клиентское приложение.
- [services/api_gateway](services/api_gateway) - внешний API для веб-приложения.
- [services/audit_service](services/audit_service) - сервис SEO-аудита.
- [services/semantic_service](services/semantic_service) - сервис семантической оценки и FF-Score.
- [services/management_service](services/management_service) - оркестратор задач и HITL.
- [services/client_api_gateway](services/client_api_gateway) - защищённый шлюз внедрения изменений.
- [services/reporting_service](services/reporting_service) - отчёты и аналитические данные.
- [services/project_integrations](services/project_integrations) - проектные интеграции.
- [adapters/wordpress-plugin](adapters/wordpress-plugin) - WordPress-плагин.
- [adapters/tilda-adapter](adapters/tilda-adapter) - адаптер Tilda.
- [tests/e2e](tests/e2e) - расширенный E2E-стенд.
- [tests/load/client_api_gateway_k6.js](tests/load/client_api_gateway_k6.js) - нагрузочный сценарий.

## Архитектура

Проект построен как набор микросервисов вокруг PostgreSQL, Redis и RabbitMQ.

| Компонент | Назначение |
| --- | --- |
| [frontend](frontend) | Интерфейс пользователя |
| [api-gateway](services/api_gateway) | Авторизация, проекты, аудиты, панель управления, передача HITL-действий |
| [audit-service](services/audit_service) | Краулинг и технический SEO-аудит |
| [semantic-service](services/semantic_service) | FF-Score, E-E-A-T и семантический анализ |
| [management-service](services/management_service) | Оркестрация задач, HITL и журнал изменений |
| [client-api-gateway](services/client_api_gateway) | Проверка HMAC-подписей и передача изменений в CMS |
| [reporting-service](services/reporting_service) | Отчёты, CSV и данные внешней аналитики |
| [project_integrations](services/project_integrations) | Хранение и отображение подключений проекта |
| [wordpress-plugin](adapters/wordpress-plugin) | Применение изменений внутри WordPress |
| [tilda-adapter](adapters/tilda-adapter) | Применение изменений на Tilda |

Подробная схема описана в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Проверки качества

В проекте есть несколько уровней проверок:

- модульные тесты серверной части в [tests/unit](tests/unit);
- тесты клиентской части в [frontend](frontend);
- расширенный E2E-стенд в [tests/e2e](tests/e2e);
- имитация WordPress API в [tests/e2e/mocks/mock_wp_api.py](tests/e2e/mocks/mock_wp_api.py);
- нагрузочный сценарий для Client API Gateway в [tests/load/client_api_gateway_k6.js](tests/load/client_api_gateway_k6.js).

E2E-стенд позволяет показать работу WordPress/Tilda/HITL без подключения реального сайта. Это важно для безопасной демонстрации: проверяется контракт взаимодействия, но реальные страницы не изменяются.

## Безопасность

В проекте используются:

- JWT-аутентификация для личного кабинета;
- HMAC SHA-256 подпись для защищённых PATCH-маршрутов;
- список разрешённых IP для Client API Gateway;
- ограничение частоты внешних запросов на проект;
- шифрование проектных учётных данных через `MASTER_ENCRYPTION_KEY`;
- однократный показ HMAC-секрета в интерфейсе;
- хранение fingerprint, key id и сроков действия вместо повторного показа секрета.

Формат HMAC-подписи описан в [docs/HMAC_CONTRACT.md](docs/HMAC_CONTRACT.md).
