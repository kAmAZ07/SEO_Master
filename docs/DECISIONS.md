## DEC-01. Уровень релиза

**Решение.** Принимаем два отдельных утверждения: «RC в опубликованном объёме» и «соответствие прежнему ТЗ». Незакрытые исторические пункты остаются видимыми и не маскируются словом «Beta», моком или отложенной проверкой.

**Что это значит для работы.**
- Для каждого требования ведётся трассировка: пункт прежнего ТЗ → REQ-раздел → AC-ID → тест → доказательство → статус.
- Допустимые статусы: выполнено, частично, заблокировано внешней предпосылкой, согласованно изменено, не выполнено.
- Промежуточная веха «исправленный P0-контур» (§1.1 ТЗ) не называется RC и не называется полным соответствием.
- Итогом работы становится legacy-compliance statement со списком выполненных пунктов, согласованных изменений и оставшихся ограничений.

## DEC-02. Tilda

**Решение.** До подтверждения поддерживаемого контракта записи Tilda-коннектор работает только на чтение и в ручном режиме. Автоматическая запись разрешается только после подтверждения контракта и теста на разрешённом стенде.

**Основание.** Официальная справка Tilda (`https://help.tilda.cc/api`) описывает методы чтения и экспорта и уведомление о публикации. Метод изменения страницы в ней не описан. Вызов POST `/updatepage` в `adapters/tilda-adapter/tilda_api_client.py` нельзя считать подтверждённым API.

**Что это значит для работы.**
- В интерфейсе вместо кнопки автопубликации показывается `manual_required` или `write_unsupported`.
- Полная автоматическая публикация в Tilda остаётся внешним блокером прежнего обещания, а не выполненным требованием.
- Подмена Tilda-native редактированием экспортированного HTML на собственном хостинге считается другим режимом развёртывания и в этот скоуп не входит.

## DEC-03. Секреты

**Решение.** HMAC-ключи хранятся во внешнем SecretProvider (защищённая конфигурация или хранилище секретов вне БД). В БД лежат только ссылки, key id и fingerprint. OAuth-токены допустимо хранить шифрованными, мастер-ключ вне БД.

**Что это значит для работы.**
- Для разработки и тестов ключи берутся из переменных окружения или Docker secrets. Пустой или демонстрационный ключ в staging и prod приводит к отказу старта соответствующей функции.
- Публикация без доступного SecretProvider закрыта.
- Хранение зашифрованных HMAC-значений в БД было бы отдельным изменением §4.1.8 прежнего ТЗ, а не буквальным соответствием ему.

## DEC-04. Приоритет задач

**Решение.** `priority_v1 = impact × confidence / effort`, где impact от 0 до 1, confidence от 0 до 1, effort от 1 до 5. Срочность выражается отдельным рангом. Порядок: ранг срочности, приоритет по убыванию, `created_at`, `task_id`.

**Основание.** Прежнее «Impact × Effort» неоднозначно: рост трудозатрат не должен повышать приоритет. Это уточнение методики, а не формула исходного ТЗ.

**Что это значит для работы.**
- В `prioritizer.py` и в модели задачи должна остаться одна формула вместо двух несовпадающих.
- При неизвестном impact показывается `unknown` и предсказуемый triage, а не подставленные 50 баллов.
- Ручной override записывается с автором и причиной.

## DEC-05. Бизнес-метрики

**Решение.** Принимаем определения из §14.2 ТЗ:
- `cost_efficiency_v1 = attributed_organic_revenue / recorded_cost` за один период и одну валюту, единица коэффициент.
- ROI отдельно: `(revenue - cost) / cost × 100%`.
- Прежнее «HITL-Efficiency» переименовывается в `HITL Execution Success v1`: доля verified и не откаченных операций среди завершившихся операций, запущенных на основании approval.

**Что это значит для работы.**
- Нет затрат, нулевая стоимость, неизвестная атрибуция или несовместимая валюта дают `null` с причиной, а не 0.
- Затраты берутся из явно введённого или импортированного набора.
- Метрика HITL Execution Success не измеряет экономию труда. Для такой метрики нужны реальные замеры.
- Сами отчёты по этим метрикам входят в ярус RC.

## DEC-06. Совместимость

**Решение.** RC проверяется на явно зафиксированном наборе версий и тем. Три последних стабильных релиза WordPress и Yoast/RankMath проверяются отдельной матрицей до утверждения полного соответствия §4.1.7. Непроверенные сочетания не маркируются как поддерживаемые.

**Что это значит для работы.**
- Для ядра фиксируется одна связка: версия WordPress, тема и SEO-плагин. Её значения записываются в манифест среды: `WP: ____, PHP: ____, тема: ____, Yoast: ____`.
- Матрица совместимости делается позже, в ярусе RC.

## DEC-07. Хранение ключа в WordPress

**Решение.** Пока наличие и стабильность Secrets API на выбранных версиях WordPress не подтверждены, нормативный fallback такой: ключ берётся из защищённой конфигурации вне webroot или из окружения и не показывается в REST.

**Что это значит для работы.**
- При необходимости оформляется уточнение прежнего требования о Secrets API.
- Установка, отключение и ротация ключа документируются в README плагина.
