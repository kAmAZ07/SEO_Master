# Фронтенд: сессия, жизненный цикл аудита, проект и владение (AL-6)

Версия: 1. Код: `frontend/src`. Основание: ТЗ §14.4, остатки AL-1 и AL-3. Тесты лежат рядом с кодом (`*.test.ts(x)`), запуск: `npm test` в `frontend/`.

## Сессия

| Что | Решение |
|---|---|
| Access-токен | `localStorage['token']`, как и раньше (`frontend/src/api/session.ts`). |
| Refresh-токен | Только в памяти страницы. После перезагрузки его нет: сессия восстанавливается, пока access-токен не истёк, дальше нужен новый вход. Перенос в HttpOnly-cookie требует изменений шлюза и в AL-6 не входит. |
| Вход ≠ наличие токена | `auth.sessionStatus`: `anonymous`, `restoring`, `authenticated`, `reauth_required`, `restore_failed`. При старте с токеном профиль запрашивается (`GET /api/auth/me`), закрытые страницы ждут ответа. |
| Обновление токена | На 401 для запроса с токеном HTTP-слой вызывает `POST /api/auth/refresh`. Параллельные 401 ждут **один** общий запрос (refresh одноразовый, ротация); запрос, отправленный со старым токеном после обновления, повторяется с новым без нового refresh. Один повтор на запрос. |
| Отказ обновления | 400/401/403/422 на refresh или отсутствие refresh-токена → сессия завершается (`reauth_required`), пользователь попадает на `/login?redirect=…` с пояснением. 503, сеть, таймаут → сессия сохраняется, вызывающий код видит исходную ошибку. |
| Публичный отчёт | 401 на запрос **без** токена обычная ошибка. Принудительного перехода на `/login` (`window.location`) больше нет: открытый публичный отчёт не теряется. |
| Выход | `logout` вызывает `POST /api/auth/logout` (best-effort), стирает токены и ключ отложенного сохранения проекта и **сбрасывает все срезы** (корневой редьюсер в `store/store.ts`). При истёкшей сессии (`reauth_required`) срез публичного аудита сохраняется, остальное очищается. Вход под другим пользователем без выхода тоже очищает данные прежнего. |
| Смена пароля | Ответ `reauth_required: true` завершает сессию (сервер отозвал все токены) и ведёт на вход с пояснением. |
| Уведомления | Отметки «прочитано» хранятся по ключу `seo_master_read_notifications:<id пользователя>`; ответ, пришедший для другого аккаунта, отбрасывается. Прежние глобальные отметки не переносятся. |

## Жизненный цикл публичного аудита

Статусы: `queued`, `running`, `completed`, `partial`, `failed`, `cancelled`, `expired` и клиентский `unknown` (`utils/auditStatus.ts`). Старые `pending`/`processing`/`in_progress` приводятся к `queued`/`running`. Незнакомый статус **не** считается «выполняется»: опрос останавливается, показывается отдельное сообщение.

- Опрос (`hooks/useAuditPolling.ts`) последовательный, 2,5 с. Прекращается на любом конечном статусе, при постоянной ошибке (404, 410), при смене аудита и размонтировании; запрос в пути отменяется (`AbortSignal`). После трёх подряд временных ошибок (сеть, таймаут, 5xx, 429) опрос останавливается и показывается «Повторить».
- Данные привязаны к `audit.activeUid`: ответ по другому `uid` или запуску отбрасывается; на маршруте без `uid` прежний результат не показывается.
- Состояния различимы: очередь/выполнение (индикатор хода, «Отменить аудит» для публичного аудита), `failed` (с кодом), `cancelled`, `expired`, `partial` (баннер с причинами и результаты), `completed` без данных, «не найден»/«истёк», «нет связи», таймаут.
- Оценка берётся только из ответа сервера: если её нет, показывается «Оценка недоступна», а не число. Везде подписана «эвристика».
- Приватный статус (`/audit/status/{uid}`) при 401/403/404 уступает публичному (`/public/audit-status/{uid}`): ошибка приватного запроса не скрывает доступный публичный отчёт.

## Сохранение аудита как проекта

`utils/projectSave.ts` и `hooks/useProjectSave.ts`: состояния `idle → saving → done | failed`. После входа по ссылке `?saveProject=1` сохранение запускается автоматически **один раз** для аудита; при ошибке показывается сообщение и «Повторить сохранение», автоповтора нет. Создание идемпотентно на сервере (`POST /api/projects` для той же области возвращает существующий проект), повтор с теми же параметрами безопасен. Если сервер отклонил присоединение аудита (`claim.status = rejected`), пользователь попадает на карточку проекта с объяснением причины.

## Проект и владение сайтом

- Карточка проекта загружается отдельно от списков (`detailsLoading`/`detailsError`/`detailsNotFound`), ответ по прежнему проекту отбрасывается; 404 и ошибка сервера различаются.
- Блок «Подтверждение владения» (`components/projects/ProjectOwnership.tsx`): состояния `unverified`, `pending`, `verified` (до даты), `stale`, проект `scope_review`; выдача файла (адрес и содержимое, токен показывается один раз), проверка с понятными текстами по кодам `errorCode`, ожидание по `Retry-After` при 429, отзыв с подтверждением. Кнопки блокируются на время запроса, ошибки объявляются через `role="alert"`, фокус переходит на инструкцию.
- Вкладка расширенного аудита объясняет отказы `domain_not_verified` (`not_verified`/`stale`/`scope_changed`), `url_out_of_scope`, `project_scope_unresolved` и ведёт к подтверждению.
- Карточка FF-Score (`ProjectFFScore.tsx`): полный балл с пометкой «эвристика», недоступное значение словами («нет данных»), оценка по старой формуле и частичная оценка подписаны отдельно.
- Несуществующий адрес открывает страницу 404.

### Проверка перед слиянием AL-6 (13.11.2026)

Для исходного `4b97ed8` PR #107 прошёл все 21 CI checks. Дополнительное ревью выявило гонки смены аккаунта, не покрытые прежним набором: поздний refresh восстанавливал токены после выхода/перезаписывал новую сессию; поздний 401 повторял старый PATCH с токеном другого аккаунта. Старые loadUser/logout/changePassword/updateProfile/login/register также могли завершиться поверх нового пользователя. Отдельные тесты сначала подтвердили отказ этих свойств, затем прошли после исправления.

Каждый HTTP-запрос теперь синхронно привязан к поколению сессии до очереди Axios. Начало новой сессии и выход меняют поколение; обычная refresh-ротация сохраняет его. Старые ответы/ошибки не перезаписывают токены, не завершают новую сессию и не запускают replay. Single-flight refresh разделён по поколениям; завершение старого promise не очищает новый. Auth-thunks передают поколение в typed metadata, Redux игнорирует завершения прежней сессии. Для новой авторизации используется `startSession`, для ротации — `setSessionTokens`; намерение сохранить аудит после входа сохраняется.

Внешняя замена access в localStorage распознаётся при проверке поколения: ожидающие старые операции не используют новый токен. Если запись storage недоступна, новая сессия использует память страницы, а не старый сохранённый токен. Это проверка конкретных гонок, не приёмка всего multi-tab/browser сценария или полной модели HttpOnly-cookie.

`safeRedirectPath` дополнительно отвергает C0/DEL и backslash. Подтверждённые TAB/LF/CR варианты браузерный URL parser превращает во внешний адрес; после исправления они отклоняются. Эксплуатация через текущий React Router не заявляется.
