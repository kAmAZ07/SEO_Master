# Tilda: чтение и ручное внедрение (Beta)

Интеграция работает в режиме `read_only_manual`. Автоматические apply, publish, rollback, изменение meta, Schema.org и перелинковки возвращают `write_unsupported`, `manual_required=true`, `receipt=null`. Они не вызывают API записи даже при включённом старом mock-флаге. Management отдельно запрещает автоматическое исполнение задач `UPDATE_TILDA_PAGE` и targets `tilda_page`.

Основание — [официальный API Tilda](https://help.tilda.cc/api): используются только GET `getprojectslist`, `getprojectinfo`, `getpageslist`, `getpage` на `https://api.tildacdn.info/v1/`. `/updatepage` не используется. API требует Business-план; documented quota — 150 запросов в час. Поддерживаемый контракт автоматической записи не подтверждён. Этот режим не доказывает исходное требование полной автоматической публикации в Tilda.

## Привязка и настройка

Сначала создайте канонический проект с UUID, правами workspace и областью URL. Сохраните Tilda public key, secret key и внешний числовой project ID в интеграции проекта. Credentials шифруются существующим vault; совпадение домена не объединяет проекты и не подтверждает права владельца.

Client Gateway использует существующее мигрированное хранилище `deployment_logs`; startup DDL и отдельная схема Tilda не нужны. Для работы требуются миграции Core/Client и Management, внутренние сервисные ключи и доступность Management. Настройки:

| Параметр | Назначение |
| --- | --- |
| `TILDA_SYNC_ENABLED` | Явное включение фонового чтения. По умолчанию Client выключает его; Compose включает через конфигурацию. |
| `TILDA_REQUESTS_PER_HOUR` | Общий локальный бюджет 1–150 запросов за скользящий час, по public-key fingerprint, включая проекты с теми же credentials. |
| `TILDA_WEBHOOK_SECRET` | Секрет не короче 32 символов для защищённого адреса callback; bootstrap генерирует его. |
| `TILDA_WEBHOOK_PUBLIC_URL` | HTTPS-база `https://<app>/api/tilda/webhook`, без query, fragment и userinfo. Без неё ручная синхронизация возможна, адрес callback отсутствует. |
| `TILDA_ADAPTER_URL`, `TILDA_INTERNAL_API_KEY`, `INTERNAL_API_KEY` | Внутренний маршрут адаптера и разные сервисные границы. Ключи не короче 32 символов. |

Включённый, но не настроенный или остановившийся обработчик делает Client readiness неуспешной. Явно отключённый режим отображается как `disabled`; уведомления и новые синхронизации не подтверждаются до готовности обработчика. Адаптер в mock-режиме не выдаёт фиктивные данные или readiness. Проверка readiness не является проверкой подписки, квоты или доступности реального API Tilda.

## Каталог и снимки

Пользователь с правом manage явно нажимает «Прочитать страницы Tilda». Client сохраняет задание, затем обработчик запрашивает сведения проекта и список страниц. Перед каждым upstream GET резервируется бюджет в БД: сбой или перезапуск не возвращает потраченный запрос. JSON `ERROR`, неверный scope/ID, HTTP-ошибки, отказы credentials и квоты не становятся успешными снимками. Повторы ограничены тремя попытками с паузами; lease и актуальная ревизия привязки защищают от позднего результата.

URL страницы берётся из явного `page_mappings` либо из подтверждённых API `customdomain` и непустого `filename`, внутри области проекта. Несопоставимая страница не получает выдуманный URL. Смена origin, scope, credentials, project ID или mapping делает старые снимки недоступными как текущий источник.

Снимки сохраняют известные поля `title`, `descr`, `published`, `filename`; missing, null и пустая строка различаются. HTML сохраняется только как SHA-256, не исполняется. Чтение каталога ограничено 500 страницами; превышение даёт явную ошибку. Интерфейс показывает дату наблюдения. Обновление статуса и пагинация читают БД, не расходуют API Tilda. Нет каталога — `total=null`, `unavailable`; измеренный пустой список — `total=0`.

## Уведомление о публикации

Владелец/администратор проекта получает секретный callback URL в панели интеграции:

```text
https://<app>/api/tilda/webhook/<canonical-project-uuid>/<capability>/published
```

Его нужно сохранить в поле Webhook URL Tilda. Это секретный адрес нашей системы, а не подпись, которую должен вычислять провайдер. Не помещайте адрес в issue, скриншоты или внешнюю аналитику. Наши access/error/HTTP-логи редактируют capability и ключи; внешний reverse proxy также должен исключать полный адрес из логов. Шаблон nginx содержит соответствующее правило.

Tilda вызывает GET с `pageid`, `projectid`, `published`, `publickey`. Обработчик проверяет capability, существующую привязку, внешние ID, public key, допустимое время и частоту. Он отвечает plain text `ok` только после commit уведомления в БД или обнаружения уже сохранённого повтора. Лимит пересылки — 3 секунды, внешнее чтение выполняется позже. При недоступном хранилище или обработчике `ok` не выдаётся. Устаревший JSON POST callback возвращает 410.

Провайдер допускает до двух повторов и задержку уведомлений 1–20 минут. UUID уведомления детерминирован по каноническому проекту, внешнему проекту, странице и published; повтор не создаёт задачу или новую публикацию. Вход ограничен 30 новыми hints в минуту на проект, published — не старше 30 дней и не дальше пяти минут в будущем. Уведомление является подсказкой повторно прочитать разрешённый источник. Оно не устанавливает ownership, mapping, approval, CMS receipt или `verified`.

## Проверка ручного внедрения

1. Получите и явно одобрите конкретную неизменяемую версию предложения.
2. Прочитайте Tilda и проверьте сопоставление target с текущим каталогом/снимком.
3. Внесите одобренный diff и опубликуйте страницу в редакторе Tilda самостоятельно.
4. В HITL явно запустите независимую проверку. Сохраняются UUID проверки, approval ID, version ID/hash и actor.

Client повторно проверяет авторитетное approval до и после анонимного публичного чтения через существующий SSRF/egress-контур. Не используются административные cookies или Tilda API как доказательство опубликованного HTML. Поддерживаются публичные predicates title, description и JSON-LD; неподдерживаемые поля, включая H1 в этом режиме, дают `manual_predicate_unsupported`.

Результаты: `manual_checking`, `manual_verified`, `manual_mismatch`, `manual_check_failed`, `manual_check_unknown`. Они живут в отдельном журнале сравнений и не переводят Task или автоматическую DeploymentOperation в `verified`. CMS-квитанция всегда отсутствует. `manual_verified` означает совпадение публичных predicates с одобренной версией на момент чтения, а не доказательство того, кто внёс изменения.

Проверка ограничена 30 секундами, пятью секундами между новыми проверками задачи и 20 новыми проверками в минуту проекта. При потерянном ответе сначала читается статус того же UUID. Только точный ответ `manual_check_not_found` позволяет повторить POST с тем же UUID; новый UUID для неизвестного результата автоматически не создаётся. Смена approval, прав или привязки во время чтения не подтверждает успех.

## HTTP-контракт и проверки

Внешние user-маршруты требуют существующую пользовательскую сессию и проверку доступа Management:

| Метод и маршрут | Действие |
| --- | --- |
| `GET /api/projects/{id}/tilda` | Capabilities, состояние обработчика, последние задания, callback только с manage. |
| `POST /api/projects/{id}/tilda/sync` | Поставить чтение в очередь, manage. |
| `GET /api/projects/{id}/tilda/pages?limit=50&offset=0` | Сохранённый каталог; limit 1–100, offset 0–10000. |
| `POST /api/hitl/tasks/{id}/manual-verify` | Явное сравнение одобренной версии. Тело: check_id, approval_id, recommendation_version_id, content_hash. |
| `GET /api/hitl/tasks/{id}/manual-checks/{check_id}` | Reconciliation того же сравнения, с актуальными правами на задачу. |

Адаптер принимает закрытый внутренний read DTO и сервисный ключ; произвольный upstream URL запрещён. Client является единственным владельцем очереди и бюджета; адаптер не создаёт второй путь исполнения CMS-команд.

Воспроизводимые уровни проверки описаны в [TESTING.md](TESTING.md): `tilda` backend-профиль проверяет протокол fixtures и запрет записи; `test_tilda_postgres.py` проверяет durable storage, конкуренцию и решения Management на настоящей отдельной PostgreSQL. Upstream Tilda и публичные ответы в этих тестах заменены явно обозначенными fixtures. Для подтверждения реального read API, тарифного плана, доставки callback за внешним HTTPS и ручной публикации нужен отдельный разрешённый аккаунт/стенд Tilda. Локальные тесты не доказывают этот уровень или supported write contract.
